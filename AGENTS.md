# Agent Instructions for sciVizModules

## Repository Overview

**sciVizModules** extends VizModules with interactivity-first Shiny modules for scientific analyses and plots. Prefer composition and extension of VizModules over parallel reimplementations of general plotting-module behavior.

**Stack**: R (>= 4.6.0), Shiny, VizModules (>= 0.6.0.9001), plotly, roxygen2 | **Version**: 0.99.0 | **License**: MIT + file LICENSE

The package targets Bioconductor (see `biocViews` in DESCRIPTION and `BIOCONDUCTOR_SUBMISSION_PLAN.md`), so keep R CMD check clean and follow Bioconductor packaging conventions.

## Repository Structure

- **R/** - source files: `*_module_ui.R` (UI), `*_module_server.R` (logic), `*_module_app.R` (examples), plus `*_helpers.R` and standalone plot functions. Package-wide helpers live in `example_data.R`, `input_helpers.R`, `palette_helpers.R` and `figure_builder_registry.R`
- **man/** - Auto-generated roxygen2 docs
- **data/** - example datasets used by tests, examples, and vignettes. `DESCRIPTION` sets no `LazyData`, so package code reaches them through `.sci_example_data()`, never by bare name. Do not ship data a dependency already ships: read it from that package with a small internal loader (`.maf_example()` reads maftools' TCGA LAML MAF, `.se_example()` the airway package's counts), guard examples with `requireNamespace()`, and in tests use the skipping helpers in `tests/testthat/helper-example-data.R`
- **data-raw/** - scripts that build the example datasets
- **vignettes/** - `quick-start.Rmd`. Every chunk is `eval = FALSE`; these are Shiny apps
- **tests/testthat/** - testthat tests, plus `testthat.R` to run the suite
- **inst/apps/** - standalone demo apps (e.g. the module gallery)
- **.github/workflows/** - `R-CMD-check.yaml` and `pkgdown.yaml`
- **DESCRIPTION** - Package metadata and dependencies
- **NAMESPACE** - Generated by roxygen2 (NEVER EDIT MANUALLY)
- **_pkgdown.yml** - curated reference index for the docs site; every new export needs an entry
- **.lintr** - Line length: 120 chars, indentation: 4 spaces
- **.Rbuildignore** - Files excluded from package build

## Modules In This Package

`alphafoldConfidence`, `cnSegmentPlot`, `deHeatmap`, `dittoBarPlot`, `dittoDimHex`, `dittoDimPlot`, `dittoDotPlot`, `dittoFreqPlot`, `dittoHeatmap`, `dittoPlot`, `dittoRidgeJitter`, `dittoScatterPlot`, `crisprScreenRank`, `doseResponse`, `enrichmentDotPlot`, `forestPlot`, `goFanPlot`, `gseaEnrichmentPlot`, `gwasQQPlot`, `mafSummary`, `maPlot`, `manhattanPlot`, `mdTrajectoryMetrics`, `michaelisMenten`, `mutationalProfile`, `mutationLollipop`, `oncoPlot`, `pcaBiplot`, `pcaEigencorPlot`, `pcaLoadingsPlot`, `pcaPairsPlot`, `pcaScreePlot`, `pkConcentrationTime`, `plateHeatmap`, `rocCurve`, `sampleDistanceHeatmap`, `samplePCA`, `structureViewer`, `survivalCurve`, `volcanoPlot`.

The modules that build their own plotly figure (the PCAtools family except `pcaBiplot`, `alphafoldConfidence`, `gseaEnrichmentPlot`, the MAF modules `oncoPlot`, `mafSummary` and `mutationLollipop`, and the data-frame modules `forestPlot`, `rocCurve`, `pkConcentrationTime`, `plateHeatmap` and `mdTrajectoryMetrics`) share their server, input layout and app scaffolding through `.sci_plot_server()`, `.sci_plot_inputs_ui()` and `.sci_object_app()` in `R/module_helpers.R`; a new module of that kind should too. `.sci_finalize_plotly()` (`R/plotly_helpers.R`) applies the uniform Axes/Legend/Lines/Plotly finishing to a figure a module builds itself. A data-frame module passes `validate = .sci_require_df` and uses `createModuleApp()` for its app; a group-colour picker goes through `setup_group_colors()` plus `.sci_palette_picker_ui()`. A categorical colour, shape or group select takes its choices from `.sci_discrete_cols()` (`R/input_helpers.R`), which keeps `facet_check()`'s columns (fewer than 50 levels) plus logicals, so an ID column is never offered. Statistics the module computes (AUCs, NCA parameters, plate Z') are attached to the figure as `attr(fig, "table")`, which `.sci_plot_server()` routes into the source-data download. Readers for non-R tool outputs are exported `read_*()` functions (`read_alphafold()`, `read_mageck()`, `read_structure()`, `read_xvg()`). Where a reference package computes the same quantity (pROC, PKNCA, fgsea), compute it in-package and test it equal to that package under `skip_if_not_installed()`, keeping the reference in Suggests.

`structureViewer` is the reference for a non-plotly widget module (see Critical Rule 6). It renders the NGLVieweR widget once per structure, restyles through `NGLVieweR_proxy()` with named representations so the camera is kept, and builds its own control strip (Reset, PNG snapshot, structure download) because `module_tack_ui()` always carries the plotly Source Data button. Wrappers of the VizModules scatter module add layers through its `fig.fn` hook via a testable internal `.<module>_layers(fig, ..., input, isolate_fn)` function (see `.pca_biplot_layers()`, `.manhattan_layers()`).

The heatmap modules (`dittoHeatmap`, `sampleDistanceHeatmap`, `deHeatmap`) wrap VizModules' `ComplexHeatmap_Heatmap` (non-plotly, InteractiveComplexHeatmap; ComplexHeatmap, InteractiveComplexHeatmap and circlize are Suggests) through `.heatmap_wrapper_server()` and friends in `R/heatmap_wrapper_helpers.R`; a new heatmap wrapper should too. The wrapper builds `list(matrix =, column_annotations =)` with `.heatmap_frame()` (key column first, names made unique), fixes and hides the base's `matrix.cols` / `rowname.col`, and hands the column order to the base as a reactive `matrix.cols` default, since the base reads the order from that input, not the data. Things that bite: an error inside the base's build observer ends the session, so preparation goes through `.sci_soft_errors()` (a `validate()` failure, shown in the wrapper's status line); rows with no variance or a missing value break Pearson distances and row scaling (`.heatmap_clean_rows()`); `column_annotations` defaults must stay static (a reactive one breaks the multiDynamicInput JS); `column_key` cannot be hidden (it shares a grid cell with the annotation editor); and reactive defaults are `isolate()`d when the base server is built, so they must fall back rather than `req()`. The somatic-mutation modules read a maftools `MAF` object or a MAF data frame through `.maf_table()` (`R/maf_helpers.R`), whose summaries are tested equal to maftools'; maftools itself is needed only for protein domains.

Each exposes the `*InputsUI()` / `*OutputUI()` / `*Server()` / `*App()` set. Run the `*App()` to inspect one interactively, or `runApp(system.file("apps/module-gallery", package = "sciVizModules"))` to see them all.

The data-frame modules are also registered with the VizModules Figure Builder via `sci_figure_builder_registry()`, so they can be arranged into a multi-panel figure with `sciFigureBuilderApp()`; `mutationalProfile` is the most recent. The dittoSeq modules (`SingleCellExperiment` input), the bulk expression modules `samplePCA`, `sampleDistanceHeatmap` and `deHeatmap` (`SummarizedExperiment`), `cnSegmentPlot` (`CNSegment`) and `michaelisMenten` (a bundle carrying a model fit), the PCAtools modules (a `pca` object) and `alphafoldConfidence` (a `read_alphafold()` result) cannot be registered - the builder's dataset catalogue holds data frames - and `structureViewer` is not a plotly figure. `forestPlot`, the GWAS modules, `crisprScreenRank`, the MAF modules (`oncoPlot`, `mafSummary`, `mutationLollipop`), `rocCurve`, `pkConcentrationTime`, `plateHeatmap` and `mdTrajectoryMetrics` take a data frame but are not registered yet.

## Coding Conventions

### VizModules Foundation

VizModules is a hard dependency (`Depends: VizModules (>= 0.6.0.9001)`) and the primary foundation for generic interactive plotting, UI organization, downloads, annotations, and module infrastructure.

- Before building or changing a module, first check whether an existing VizModules module, helper, or wrapper pattern covers the general behavior. Extend it with science-specific defaults, controls, data preparation, annotations, or validation instead of recreating it.
- Every VizModules plot module follows the shared `*InputsUI(id, ...)`, `*OutputUI(id)`, and `*Server(id, data = reactive(...), ...)` contract. Preserve this contract when wrapping or composing a base module.
- Use `defaults` to set scientific defaults. Use `hide.inputs` and `hide.tabs` to enforce fixed values without exposing the corresponding generic controls.
- Prefer documented VizModules arguments and helpers over local replacements. Commonly useful ones, grouped by what they do:
  - **Inputs and layout**: `organize_inputs()`, `module_tack_ui()`, `hide_input()` / `show_input()` / `toggle_input_cell()`, `viz_select_input()` / `update_viz_select()`, `multiColorPicker()` / `updateMultiColorPicker()`, `multiDynamicInput()` / `updateMultiDynamicInput()`, and the uniform input blocks (`uniform_axes_inputs_ui()`, `uniform_legend_inputs_ui()`, `uniform_lines_inputs_ui()`, `uniform_plotly_inputs_ui()`, `uniform_annotation_inputs_ui()`) with their reset counterparts (`reset_axes_inputs()`, `reset_legend_inputs()`, `reset_lines_inputs()`, `reset_plotly_inputs()`, `reset_annotation_inputs()`), plus `uniform_subplot_spacing_inputs_ui()` / `subplot_spacing_defaults()` for a Facet tab's spacing controls.
  - **Defaults and server-side stores**: `get_default()`, `setup_reactive_defaults()`, `setup_auto_update_logic()`, `setup_group_colors()`, `setup_axis_range()`, `resolve_palette()`, `setup_manual_edits()` / `finalize_manual_edits()` / `reset_manual_edits()`, and for a group colour picker `default_group_colors()` (validates and hex-normalises a mapping in `defaults`) with `reset_group_colors()` (restores the picker on Reset). See "Avoiding Double Renders" below.
  - **Server boilerplate**: `require_data_frame()` wraps a data-frame module's `data` reactive; `blank_to_null()` turns a select's `""` (or `NA`, or a missing input) into `NULL`, and `nz_value()` tests for a usable string without erroring on `NULL`; `with_stable_seed()` builds a jittered plot under a fixed seed so the points stay put across rebuilds; `facet_check()`, `flatten_palette_options()`, and `as_plotted()` / `adjusted_values()` / `adjustment_fn()` for anything drawn over an adjusted axis.
  - **Plot finishing**: `apply_title_layout()`, `create_axis_styles()`, `apply_subplot_axis_styling()`, `axis_titles_as_annotations()`, `apply_axis_title_to_annotations()`, `reset_axis_title_text()`, `add_reference_lines()`, `add_plot_config()`, `apply_plotly_newshape()`, `apply_render_margins()`, `apply_legend_styling()` / `apply_legend_inputs()`, `add_size_legend()` (the circle size legend plotly drops when marker size encodes a column, as the DotPlot module and `dittoDotPlot` draw it), `empty_plot()`. A module that renders `uniform_legend_inputs_ui()` must apply all of it (`legend.show`, `legend.font.family`, `legend.font.color` and the two sizes), and one that renders the shape controls of `uniform_plotly_inputs_ui()` must call `apply_plotly_newshape()`; a plot without cartesian axes passes `include.shapes = FALSE` and `include.modebar.buttons = FALSE` instead. A figure split into panels (e.g. by `split.by`) passes `facet.by` to `add_plot_config()`, which drops the editable main title, styles its shared axis and panel titles with `apply_axis_title_to_annotations()`, and swaps the main title inputs for the `facet.title.*` ones as the split changes (`toggle_facet_title_inputs()`; a plot that always facets hides `main_title_input_ids` instead).
  - **Statistics**: `uniform_stats_inputs_ui()` / `reset_stats_inputs()`, `compute_pairwise_stats()`, `create_stat_annotations()`, `apply_stat_annotations()`, `stat_bracket_y_max()` / `stat_bracket_headroom()`, `note_brackets_skipped()`, `generate_pair_strings()` / `parse_pair_strings()` / `default_stat_pairs()`.
  - **Point highlighting and labels**: `parse_highlight_values()`, `apply_highlight_styling()`, `create_highlight_annotations()`, `create_selected_annotations()`, `merge_annotation_sets()`.
  - **Export**: `collect_source_data()`, `create_source_download_handler()`, `draw_to_svg()` / `draw_to_png()`.
  - **Data tables and expressions**: `dataFilterUI()` / `dataFilterServer()`, `resolve_column_targets()`, `safe_eval_filter()` / `validate_expression()`.
- For faceted / multi-panel figures, reuse the facet toolkit rather than hand-rolling layout maths: `resolve_facet_sharing()`, `resolve_facet_layout()`, `apply_facet_subplot_spacing()`, `build_facet_annotations()`, and `build_facet_panel_borders()`.
- For a new scientific module, create bespoke plotting or module code only when VizModules does not provide an appropriate base. Reuse its input organization, layout, download, and plotly conventions where applicable.
- Build plots with plotly wherever plotly can do the job - the VizModules helpers this package leans on assume it (see Critical Rule 6 for when a non-plotly widget is acceptable). Do not assume that every argument of an underlying `dittoViz`, `dittoSeq`, or `plotthis` function is exposed through a VizModules module; verify its documented signature first.

### Avoiding Double Renders

Three situations, three different tools. Picking the wrong one gives a plot that
rebuilds twice per change - cheap on a toy dataset, painful on a real one.

1. **A parent app drives a module parameter** -> a reactive entry in `defaults`.
   Resolved server-side in the same flush as the data, so the plot renders once
   and the control stays populated and editable. Not `update*Input()` from the
   parent, which is an async browser round-trip. Create the store with
   `setup_reactive_defaults(defaults, input, session)` as the **first** statement
   of `moduleServer()`, and pass it to `setup_auto_update_logic(input, params)`.
   Reads must stay in the literal form `isolate_fn(input$key)`, because the
   wrapper inspects `substitute()` to decide whether to redirect to the store.
2. **A module updates one of its own ordinary inputs** -> `freezeReactiveValue()`
   immediately before the update, in the same branch. Never wrap
   `renderPlotly()` in a catch-all `tryCatch()`: the pause arrives as a silent
   condition, and swallowing it turns a clean pause into a blank plot.
3. **A module updates an input that `renderUI()` rebuilds** -> a server-side
   store. Freezing cannot help: it pauses only readers that run after it in that
   flush, and at startup the plot output runs first. Use
   `setup_group_colors()` for a `multiColorPicker()` (seed it inside the
   `renderUI()` with the same `resolve_palette()` result the picker is built
   from, and read `isolate_fn(palette_store())` in the plot) and
   `setup_axis_range()` for y-limit controls (seed it beside **every**
   `update*Input()` that sets them).

`default_group_colors(defaults, key)` validates a caller-supplied mapping before
it reaches `resolve_palette()`'s `manual_colors` argument, and
`reset_group_colors()` puts the picker back to it on Reset.

### Debouncing Free Text

`textInput()` and `textAreaInput()` report on **every keystroke**, so a plot that
reads one directly is rebuilt once per character - and for a gene list or an
expression, most of those characters are a state the plot cannot use. Use
`.sci_debounced_input(input, "key", params)` (`R/input_helpers.R`), created
**once** in the module server body; inside another reactive it rebuilds the timer
and does nothing. 700ms matches VizModules. Select, numeric, checkbox and slider
inputs report discrete choices and need nothing.

### CSS Containment

Any stylesheet or inline `tags$style()` this package ships lands in the host
app's document. There is no shadow DOM and no automatic scoping, and every plot
module pulls a colour picker in, so one bare selector restyles an app that merely
wanted one plot. VizModules was bitten by this three times (#355).

Anchor every rule on a class this package invents - `.scivizmodules-` or
`.sci-`. **Judge by the leftmost class: if you did not invent it, the rule is not
scoped.** `.navbar`, `.well`, `.nav-tabs`, `.form-group`, `.selectize-dropdown`,
`.option`, `.btn` and friends are Bootstrap's, selectize's or DT's, not yours.

Layout belongs in a stylesheet, not an inline `style=` (which a host app can only
override with `!important`); per-instance values go through a CSS custom
property. Do not assume the parent's padding - use `gap`, and `min-width: 0` on
flex children. A dropdown or popover parented to `<body>` cannot be reached by a
descendant selector, so give it a marker class of its own.

This package currently ships no package-level CSS; the only stylesheet is the
module gallery's, scoped to `.scivizmodules-gallery`. Keep it that way.

### Module Structure Pattern

Each module has at least 3 files: `*_module_ui.R` (InputsUI/OutputUI functions), `*_module_server.R` (Server function), `*_module_app.R` (`*App()` example). A 4th file of module-specific helpers is allowed, e.g. `goFanPlot_helpers.R`. Standalone plotting functions get their own file, e.g. `goFanPlot.R`, `cnSegmentPlot.R`.

Keep the plotting function usable on its own, independent of Shiny. The module server should be a thin layer that maps inputs onto that function's arguments and then applies the shared VizModules finalize stack.

Where the UI and server both need the same defaults or input choices, factor them into a shared internal helper rather than duplicating the literal in both files — the two drift otherwise (see `.cn_seg_base_defaults()` and friends in `R/cnSegmentPlot.R`).

### Critical Namespace Pattern for Wrapper Modules

```r
wrapperServer <- function(id, data_reactive) {
    # Process data INSIDE moduleServer to access namespaced inputs
    filtered_data <- moduleServer(id, function(input, output, session) {
        reactive({ /* use input$customField here */ })
    })
    # Call base module OUTSIDE to avoid double-namespacing (id-id-inputName)
    baseModuleServer(id, filtered_data)
}
```

In UI: Use `NS(id)` for wrapper's inputs, pass bare `id` to base module UI functions.

## Common Issues

| Issue | Solution |
|-------|----------|
| "object not exported by namespace" | Run `devtools::document()` to regenerate NAMESPACE |
| `document()` rewrites the whole NAMESPACE | DESCRIPTION records `Config/roxygen2/version`. A newer installed roxygen2 reformats every entry and bumps the stamp. Keep the diff scoped: revert the unrelated hunks, or agree to the reformat deliberately rather than as a side effect |

| `'scattergl' objects don't have these attributes: 'hoveron'` | Benign plotly warning from `toWebGL()` on line traces; noisy in test output, not a failure |
| Faceted figure loses its draggable axis titles | `axis_titles_as_annotations()` intentionally skips multi-panel figures; use `apply_axis_title_to_annotations()` instead |
| "object 'example_sce' not found" in package code | No `LazyData`, so bundled datasets are not promises in the namespace. Use `.sci_example_data("example_sce")`; in an `@examples` block or a test, call `data()` first |
| A plot renders two or three times for one change | See "Avoiding Double Renders" above - pick the right one of reactive `defaults`, `freezeReactiveValue()`, or a server-side store |
| `shiny::testServer()` cannot drive a plotly output | Expected; assert on the server's own reactives instead, or verify structurally with `plotly::plotly_build()` |

## Critical Rules

1. **Build upon VizModules whenever possible** - start from an existing VizModules module or helper; add only the scientific specialization this package owns. Verify the installed API before calling it.
2. **NEVER edit NAMESPACE manually** - always use `devtools::document()`
3. **ALWAYS run `devtools::document()`** after changing roxygen2 comments or signatures
4. **Run `devtools::test()`** after changes to verify the testthat test suite passes; also test modules interactively via example apps
5. **Follow namespace pattern strictly** for wrapper modules (see Coding Conventions)
6. **Strongly prefer plotly** - the shared finishing helpers, manual-edit persistence, the Figure Builder and the source-data images all assume a plotly figure, so a module built from scratch should be plotly unless plotly has no reasonable equivalent. A non-plotly htmlwidget with Shiny bindings is acceptable in that case (e.g. a 3D molecular viewer via NGLVieweR or r3dmol; VizModules' own `ComplexHeatmap_Heatmap` is another). Such a module must say so in its docs, and supply its own image export. To appear in the Figure Builder export and source archive it needs `vector_svg` / `raster_png` renderers (built with `draw_to_svg()` / `draw_to_png()`); without them it contributes no artwork there
7. **Document missing features** - clearly note functionality unavailable in plotly
8. **Use `VizModules::organize_inputs()`** helper for consistent UI layouts
9. **Keep changes scoped** - do not let generated-file churn (NAMESPACE reformatting, roxygen version bumps) ride along with a behavioral change
10. **Every module select is a `viz_select_input()`** - never `shiny::selectInput()`. A column of gene names is unusable otherwise, and two VizModules 0.5.0 fixes land only on the virtual select. `tests/testthat/test-select-inputs.R` enforces this
11. **Scope every CSS selector** on a class this package invents (see "CSS Containment")
12. **Load the matching VizModules skill before module work** - adding, wrapping or wiring a module starts from `vizmodules-custom-module`, `vizmodules-new-module` or `vizmodules-app` (see "Use the VizModules Skills for Module Work")

## Best Practices

- Avoid `sapply` usage, it is unsafe in package code. Prefer `vapply` with an explicit `FUN.VALUE`.
- When changing a shared plotting function, keep existing single-input behavior byte-identical unless the change is the point; the existing tests are the regression guard and should stay green untouched.
- Prefer verifying plotly output structurally (`plotly::plotly_build()`, then inspect `x$data` / `x$layout`) over eyeballing; reserve interactive checks for layout and legibility questions that structure cannot answer.

These instructions are a starting point, not an authority. Verify against the code before relying on any specific claim here, and correct this file when you find it stale.
