# Agent Instructions for sciVizModules

## Repository Overview

**sciVizModules** extends VizModules with interactivity-first Shiny
modules for scientific analyses and plots. Prefer composition and
extension of VizModules over parallel reimplementations of general
plotting-module behavior.

**Stack**: R (\>= 4.6.0), Shiny, VizModules (\>= 0.6.0), plotly,
roxygen2 \| **Version**: 0.99.0 \| **License**: MIT + file LICENSE

The package targets Bioconductor (see `biocViews` in DESCRIPTION and
`BIOCONDUCTOR_SUBMISSION_PLAN.md`), so keep R CMD check clean and follow
Bioconductor packaging conventions.

## Repository Structure

- **R/** - source files: `*_module_ui.R` (UI), `*_module_server.R`
  (logic), `*_module_app.R` (examples), plus `*_helpers.R` and
  standalone plot functions. Package-wide helpers live in
  `example_data.R`, `input_helpers.R`, `palette_helpers.R` and
  `figure_builder_registry.R`. `module_showcase.R` holds the
  example-data catalogue and the showcase registry every module needs an
  entry in; `moduleGallery_app.R` builds the gallery from it (see
  “Adding a Module: Gallery, App and Figure Builder”)
- **man/** - Auto-generated roxygen2 docs
- **data/** - example datasets used by tests, examples, and vignettes.
  `DESCRIPTION` sets no `LazyData`, so package code reaches them through
  [`.sci_example_data()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_example_data.md),
  never by bare name. Do not ship data a dependency already ships: read
  it from that package with a small internal loader
  ([`.maf_example()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_maf_example.md)
  reads maftools’ TCGA LAML MAF,
  [`.se_example()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_se_example.md)
  the airway package’s counts), guard examples with
  [`requireNamespace()`](https://rdrr.io/r/base/ns-load.html), and in
  tests use the skipping helpers in
  `tests/testthat/helper-example-data.R`
- **data-raw/** - scripts that build the example datasets
- **vignettes/** - `quick-start.Rmd`. Every chunk is `eval = FALSE`;
  these are Shiny apps
- **tests/testthat/** - testthat tests, plus `testthat.R` to run the
  suite
- **inst/apps/module-gallery/** - a thin `app.R` deploying
  [`sciModuleGalleryApp()`](https://j-andrews7.github.io/sciVizModules/reference/sciModuleGalleryApp.md)
  (to shinyapps.io or Posit Connect), with its rsconnect `manifest.json`
  (build-ignored)
- **.github/workflows/** - `R-CMD-check.yaml` and `pkgdown.yaml`
- **DESCRIPTION** - Package metadata and dependencies
- **NAMESPACE** - Generated by roxygen2 (NEVER EDIT MANUALLY)
- \*\*\_pkgdown.yml\*\* - curated reference index for the docs site;
  every new export needs an entry
- **.lintr** - Line length: 120 chars, indentation: 4 spaces
- **.Rbuildignore** - Files excluded from package build

`dittoHeatmap`, `dittoPlot`, `dittoRidgeJitter`, `dittoScatterPlot`,
`crisprScreenRank`, `doseResponse`, `enrichmentDotPlot`, `forestPlot`,
`goFanPlot`, `gseaEnrichmentPlot`, `gwasQQPlot`, `mafSummary`, `maPlot`,
`manhattanPlot`, `mdTrajectoryMetrics`, `michaelisMenten`,
`mutationalProfile`, `mutationLollipop`, `oncoPlot`, `pcaBiplot`,
`pcaEigencorPlot`, `pcaLoadingsPlot`, `pcaPairsPlot`, `pcaScreePlot`,
`pkConcentrationTime`, `plateHeatmap`, `rocCurve`,
`sampleDistanceHeatmap`, `samplePCA`, `structureViewer`,
`survivalCurve`, `volcanoPlot`.

The modules that build their own plotly figure (the PCAtools family
except `pcaBiplot`, `alphafoldConfidence`, `gseaEnrichmentPlot`, the MAF
modules `oncoPlot`, `mafSummary` and `mutationLollipop`, and the
data-frame modules `forestPlot`, `rocCurve`, `pkConcentrationTime`,
`plateHeatmap`, `mdTrajectoryMetrics` and `survivalCurve`) share their
server, input layout and app scaffolding through
[`.sci_plot_server()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_plot_server.md),
[`.sci_plot_inputs_ui()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_plot_inputs_ui.md)
and
[`.sci_object_app()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_object_app.md)
in `R/module_helpers.R`; a new module of that kind should too.
[`.sci_finalize_plotly()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_finalize_plotly.md)
(`R/plotly_helpers.R`) applies the uniform Axes/Legend/Lines/Plotly
finishing to a figure a module builds itself. It styles every axis, so a
panel whose axes must keep their own settings (the risk table’s
gridlines) names them in `attr(fig, "fixed.axes")`; and since plotly
draws a shared axis’s lines on one panel only, it boxes each panel of a
`subplot()` with shared axes through
[`.sci_shared_panel_borders()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_shared_panel_borders.md).
A panel that needs gridlines or borders of its own, independent of its
neighbours, gets an x axis of its own matched to theirs
(`matches = "x"`, as `survivalCurve`‘s risk table does). A data-frame
module passes `validate = .sci_require_df` and uses `createModuleApp()`
for its app; a group-colour picker goes through `setup_group_colors()`
plus
[`.sci_palette_picker_ui()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_palette_picker_ui.md).
A categorical colour, shape or group select takes its choices from
[`.sci_discrete_cols()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_discrete_cols.md)
(`R/input_helpers.R`), a thin wrapper of VizModules’
`discrete_choices()` that also accepts non-data-frame metadata and, with
`numeric = TRUE`, low-cardinality numeric columns (a dose). It keeps
`facet_check()`‘s columns (fewer than 50 levels) plus logicals, so an ID
column is never offered, and takes `keep` for the column a caller named
in `defaults`, which is offered whatever its size, as in the VizModules
modules. A confidence band or error bars around a line go through
[`VizModules::linePlot()`](https://j-andrews7.github.io/VizModules/reference/linePlot.html)
with `error.type = "columns"` and `error.ribbon` / `error.bar`, so the
band takes its line’s colour and legend group as in the line plot
module, rather than hand-built fill traces; work out a group’s
half-width with
[`VizModules::error_bar_halfwidth()`](https://j-andrews7.github.io/VizModules/reference/error_bar_halfwidth.html)
(`pkConcentrationTime`’s group means), and draw a step function from
duplicated step coordinates (`survivalCurve`’s
[`.km_steps()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_km_steps.md)).
`ggplotly()` cannot convert survminer’s stepped confidence band and
drops it. Statistics the module computes (AUCs, NCA parameters, plate
Z’, Kaplan-Meier medians and the log-rank test) are attached to the
figure as `attr(fig, "table")`, which
[`.sci_plot_server()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_plot_server.md)
routes into the source-data download. A module with more than one table
attaches a named list of them, which the download writes as one CSV each
(`survivalCurve`’s `strata` summary and, while pairwise comparisons are
on, its `pairwise` table); the plot function itself keeps a single
`"table"` and returns the others as attributes of their own
(`attr(fig, "pairwise")`). Pairwise tests are adjusted across the
comparisons made, carry an effect size with its interval, never hide
non-significant results, and come with interpretation notes in the
function’s Details and the vignette. Readers for non-R tool outputs are
exported `read_*()` functions
([`read_alphafold()`](https://j-andrews7.github.io/sciVizModules/reference/read_alphafold.md),
[`read_mageck()`](https://j-andrews7.github.io/sciVizModules/reference/read_mageck.md),
[`read_structure()`](https://j-andrews7.github.io/sciVizModules/reference/read_structure.md),
[`read_xvg()`](https://j-andrews7.github.io/sciVizModules/reference/read_xvg.md)).
Where a reference package computes the same quantity (pROC, PKNCA,
fgsea, survminer), compute it in-package and test it equal to that
package under `skip_if_not_installed()`, keeping the reference in
Suggests.

`structureViewer` is the reference for a non-plotly widget module (see
Critical Rule 6). It renders the NGLVieweR widget once per structure,
restyles through `NGLVieweR_proxy()` with named representations so the
camera is kept, and builds its own control strip (Reset, PNG snapshot,
structure download) because `module_tack_ui()` always carries the plotly
Source Data button. Wrappers of the VizModules scatter module add layers
through its `fig.fn` hook via a testable internal
`.<module>_layers(fig, ..., input, isolate_fn)` function (see
[`.pca_biplot_layers()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_pca_biplot_layers.md),
[`.manhattan_layers()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_manhattan_layers.md)).
The scatter server draws trajectories (arrowheads as annotations), then
runs `fig.fn`, then adds the Marginals tab’s strips with
`add_marginal_plots()`, which shrinks the main panel and moves
paper-anchored shapes and annotations into it. So a layer function
appends to `layout$annotations` and `layout$shapes` rather than
replacing them, and a layer on paper coordinates still lands in the
panel. A wrapper whose axes are not distributions (genomic position,
expected quantiles, rank, dose) hides “Marginals” by default, as
`manhattanPlot`, `gwasQQPlot`, `crisprScreenRank` and `doseResponse` do.

The heatmap modules (`dittoHeatmap`, `sampleDistanceHeatmap`,
`deHeatmap`) wrap VizModules’ `ComplexHeatmap_Heatmap` (non-plotly,
InteractiveComplexHeatmap; ComplexHeatmap, InteractiveComplexHeatmap and
circlize are Suggests) through
[`.heatmap_wrapper_server()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_heatmap_wrapper_server.md)
and friends in `R/heatmap_wrapper_helpers.R`; a new heatmap wrapper
should too. The wrapper builds `list(matrix =, column_annotations =)`
with
[`.heatmap_frame()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_heatmap_frame.md)
(key column first, names made unique), fixes and hides the base’s
`matrix.cols` / `rowname.col`, and hands the column order to the base as
a reactive `matrix.cols` default, since the base reads the order from
that input, not the data. Things that bite: an error inside the base’s
build observer ends the session, so preparation goes through
[`.sci_soft_errors()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_soft_errors.md)
(a `validate()` failure, shown in the wrapper’s status line); rows with
no variance or a missing value break Pearson distances and row scaling
([`.heatmap_clean_rows()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_heatmap_clean_rows.md));
`column_annotations` defaults must stay static (a reactive one breaks
the multiDynamicInput JS); `column_key` cannot be hidden (it shares a
grid cell with the annotation editor); and reactive defaults are
`isolate()`d when the base server is built, so they must fall back
rather than `req()`. The somatic-mutation modules read a maftools `MAF`
object or a MAF data frame through
[`.maf_table()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_maf_table.md)
(`R/maf_helpers.R`), whose summaries are tested equal to maftools’;
maftools itself is needed only for protein domains.

Each exposes the `*InputsUI()` / `*OutputUI()` / `*Server()` / `*App()`
set. Run the `*App()` to inspect one interactively, or
[`sciModuleGalleryApp()`](https://j-andrews7.github.io/sciVizModules/reference/sciModuleGalleryApp.md)
to see them all: every module on its own tab under a menu by field, each
opening on its example data with its main features switched on, and the
Figure Builder. A module’s server starts only when its tab is first
opened, so the gallery is the fastest way to click through every module
after a change.

The data-frame modules flagged `figure_builder = TRUE` in the showcase
registry are also offered by the VizModules Figure Builder through
[`sci_figure_builder_registry()`](https://j-andrews7.github.io/sciVizModules/reference/sci_figure_builder_registry.md),
which is derived from that registry, so they can be arranged into a
multi-panel figure with
[`sciFigureBuilderApp()`](https://j-andrews7.github.io/sciVizModules/reference/sciFigureBuilderApp.md).
The dittoSeq modules (`SingleCellExperiment` input), the bulk expression
modules `samplePCA`, `sampleDistanceHeatmap` and `deHeatmap`
(`SummarizedExperiment`), `cnSegmentPlot` (`CNSegment`) and
`michaelisMenten` (a bundle carrying a model fit), the PCAtools modules
(a `pca` object) and `alphafoldConfidence` (a
[`read_alphafold()`](https://j-andrews7.github.io/sciVizModules/reference/read_alphafold.md)
result) cannot be registered - the builder’s dataset catalogue holds
data frames - and `structureViewer` is not a plotly figure.
`forestPlot`, the GWAS modules, `crisprScreenRank`, the MAF modules
(`oncoPlot`, `mafSummary`, `mutationLollipop`), `rocCurve`,
`pkConcentrationTime`, `plateHeatmap` and `mdTrajectoryMetrics` take a
data frame but are not flagged yet.


## Coding Conventions

### VizModules Foundation

VizModules is a hard dependency (`Depends: VizModules (>= 0.6.0)`) and
the primary foundation for generic interactive plotting, UI
organization, downloads, annotations, and module infrastructure.

- Before building or changing a module, first check whether an existing
  VizModules module, helper, or wrapper pattern covers the general
  behavior. Extend it with science-specific defaults, controls, data
  preparation, annotations, or validation instead of recreating it.
- Every VizModules plot module follows the shared `*InputsUI(id, ...)`,
  `*OutputUI(id)`, and `*Server(id, data = reactive(...), ...)`
  contract. Preserve this contract when wrapping or composing a base
  module.
- Use `defaults` to set scientific defaults. Use `hide.inputs` and
  `hide.tabs` to enforce fixed values without exposing the corresponding
  generic controls.
- Prefer documented VizModules arguments and helpers over local
  replacements. Commonly useful ones, grouped by what they do:
  - **Inputs and layout**: `organize_inputs()`, `module_tack_ui()`,
    `hide_input()` / `show_input()` / `toggle_input_cell()`,
    `viz_select_input()` / `update_viz_select()`, `multiColorPicker()` /
    `updateMultiColorPicker()`, `multiDynamicInput()` /
    `updateMultiDynamicInput()`, and the uniform input blocks
    (`uniform_axes_inputs_ui()`, `uniform_legend_inputs_ui()`,
    `uniform_lines_inputs_ui()`, `uniform_plotly_inputs_ui()`,
    `uniform_annotation_inputs_ui()`) with their reset counterparts
    (`reset_axes_inputs()`, `reset_legend_inputs()`,
    `reset_lines_inputs()`, `reset_plotly_inputs()`,
    `reset_annotation_inputs()`), plus
    `uniform_subplot_spacing_inputs_ui()` / `subplot_spacing_defaults()`
    for a Facet tab’s spacing controls.
  - **Defaults and server-side stores**: `get_default()`,
    `setup_reactive_defaults()`, `setup_auto_update_logic()`,
    `setup_group_colors()`, `setup_axis_range()`, `resolve_palette()`,
    `setup_manual_edits()` / `finalize_manual_edits()` /
    `reset_manual_edits()`, and for a group colour picker
    `default_group_colors()` (validates and hex-normalises a mapping in
    `defaults`) with `reset_group_colors()` (restores the picker on
    Reset). See “Avoiding Double Renders” below.
  - **Server boilerplate**: `require_data_frame()` wraps a data-frame
    module’s `data` reactive; `blank_to_null()` turns a select’s `""`
    (or `NA`, or a missing input) into `NULL`, and `nz_value()` tests
    for a usable string without erroring on `NULL`; `with_stable_seed()`
    builds a jittered plot under a fixed seed so the points stay put
    across rebuilds; `facet_check()`, `discrete_choices()` (a colour,
    shape, group or fill select’s categorical choices, capped at 50
    levels), `flatten_palette_options()`, and `as_plotted()` /
    `adjusted_values()` / `adjustment_fn()` for anything drawn over an
    adjusted axis.
  - **Plot finishing**: `apply_title_layout()`, `create_axis_styles()`,
    `apply_subplot_axis_styling()`, `axis_titles_as_annotations()`,
    `apply_axis_title_to_annotations()`, `reset_axis_title_text()`,
    `add_reference_lines()`, `add_plot_config()`,
    `apply_plotly_newshape()`, `apply_render_margins()`,
    `apply_legend_styling()` / `apply_legend_inputs()`,
    `add_size_legend()` (the circle size legend plotly drops when marker
    size encodes a column, as the DotPlot module and `dittoDotPlot` draw
    it; give it the plot’s size-scale `limits` and `size.range` so its
    circles match the points, and `breaks` to leave out an empty size-0
    circle), `empty_plot()`. A module that renders
    `uniform_legend_inputs_ui()` must apply all of it (`legend.show`,
    `legend.font.family`, `legend.font.color` and the two sizes), and
    one that renders the shape controls of `uniform_plotly_inputs_ui()`
    must call `apply_plotly_newshape()`; a plot without cartesian axes
    passes `include.shapes = FALSE` and
    `include.modebar.buttons = FALSE` instead. A figure split into
    panels (e.g. by `split.by`) passes `facet.by` to
    `add_plot_config()`, which drops the editable main title, styles its
    shared axis and panel titles with
    `apply_axis_title_to_annotations()`, and swaps the main title inputs
    for the `facet.title.*` ones as the split changes
    (`toggle_facet_title_inputs()`; a plot that always facets hides
    `main_title_input_ids` instead).
  - **Statistics**: `uniform_stats_inputs_ui()` /
    `reset_stats_inputs()`, `compute_pairwise_stats()`,
    `create_stat_annotations()`, `apply_stat_annotations()`,
    `stat_bracket_y_max()` / `stat_bracket_headroom()`,
    `note_brackets_skipped()`, `generate_pair_strings()` /
    `parse_pair_strings()` / `default_stat_pairs()`.
  - **Point highlighting and labels**: `parse_highlight_values()`,
    `apply_highlight_styling()`, `create_highlight_annotations()`,
    `create_selected_annotations()`, `merge_annotation_sets()`.
  - **Export**: `collect_source_data()`,
    `create_source_download_handler()`, `draw_to_svg()` /
    `draw_to_png()`.
  - **Data tables and expressions**: `dataFilterUI()` /
    `dataFilterServer()`, `resolve_column_targets()`,
    `safe_eval_filter()` / `validate_expression()`.
- For faceted / multi-panel figures, reuse the facet toolkit rather than
  hand-rolling layout maths: `resolve_facet_sharing()`,
  `resolve_facet_layout()`, `apply_facet_subplot_spacing()`,
  `build_facet_annotations()`, and `build_facet_panel_borders()`.
- For a new scientific module, create bespoke plotting or module code
  only when VizModules does not provide an appropriate base. Reuse its
  input organization, layout, download, and plotly conventions where
  applicable.
- Build plots with plotly wherever plotly can do the job - the
  VizModules helpers this package leans on assume it (see Critical Rule
  6 for when a non-plotly widget is acceptable). Do not assume that
  every argument of an underlying `dittoViz`, `dittoSeq`, or `plotthis`
  function is exposed through a VizModules module; verify its documented
  signature first.

### Use the VizModules Skills for Module Work

Before adding a module, wrapping a base module, or wiring modules into
an app, load the matching VizModules agent skill and follow it. They
encode the conventions this file only summarizes (reactive defaults,
double-render avoidance, manual-edit persistence, the uniform input
helpers, CSS containment), and they are kept in step with each
VizModules release. If they are not already in `.claude/skills/` (or
`.agents/skills/`, `.github/skills/`), install them first with
`VizModules::use_vizmodules_skills(".", client = "claude")`, which
copies them from the installed VizModules (`overwrite = TRUE` refreshes
them after a VizModules upgrade).

### VizModules Reference Sources

Use these sources before guessing at a VizModules API or adding a
replacement helper:

1.  **The bundled agent skills.** VizModules ships three under
    `inst/skills/`, installable into this project with
    `VizModules::use_vizmodules_skills(".", client = "claude")` (also
    `"agents"` for `.agents/skills`, `"copilot"` for `.github/skills`).
    Start here - they are written for this job and are far cheaper than
    reading the vignettes:
    - `vizmodules-app` - wiring modules into an app: `defaults`,
      `hide.inputs` / `hide.tabs`, the Stats tab, `createModuleApp()`,
      the data filter, the figure builder, source-data export. Its
      `references/module-inventory.md` is the generated, authoritative
      list of every module’s mapping keys, colour key and tab names.
    - `vizmodules-custom-module` - wrapping or extending a base module,
      which is what most of this package does. Its
      `references/reactive-and-rerender.md` is the canonical write-up of
      the double-render problem.
    - `vizmodules-new-module` - authoring a module inside VizModules
      itself. Its `references/css-containment.md` and
      `references/uniform-helpers.md` apply here too.
2.  Installed package help and vignettes:
    [`help(package = "VizModules")`](https://j-andrews7.github.io/VizModules/reference),
    [`vignette("quick-start", package = "VizModules")`](https://j-andrews7.github.io/VizModules/articles/quick-start.html),

### Avoiding Double Renders

Three situations, three different tools. Picking the wrong one gives a
plot that rebuilds twice per change - cheap on a toy dataset, painful on
a real one.

1.  **A parent app drives a module parameter** -\> a reactive entry in
    `defaults`. Resolved server-side in the same flush as the data, so
    the plot renders once and the control stays populated and editable.
    Not `update*Input()` from the parent, which is an async browser
    round-trip. Create the store with
    `setup_reactive_defaults(defaults, input, session)` as the **first**
    statement of `moduleServer()`, and pass it to
    `setup_auto_update_logic(input, params)`. Reads must stay in the
    literal form `isolate_fn(input$key)`, because the wrapper inspects
    [`substitute()`](https://rdrr.io/r/base/substitute.html) to decide
    whether to redirect to the store.
2.  **A module updates one of its own ordinary inputs** -\>
    `freezeReactiveValue()` immediately before the update, in the same
    branch. Never wrap `renderPlotly()` in a catch-all
    [`tryCatch()`](https://rdrr.io/r/base/conditions.html): the pause
    arrives as a silent condition, and swallowing it turns a clean pause
    into a blank plot.
3.  **A module updates an input that `renderUI()` rebuilds** -\> a
    server-side store. Freezing cannot help: it pauses only readers that
    run after it in that flush, and at startup the plot output runs
    first. Use `setup_group_colors()` for a `multiColorPicker()` (seed
    it inside the `renderUI()` with the same `resolve_palette()` result
    the picker is built from, and read `isolate_fn(palette_store())` in
    the plot) and `setup_axis_range()` for y-limit controls (seed it
    beside **every** `update*Input()` that sets them).

`default_group_colors(defaults, key)` validates a caller-supplied
mapping before it reaches `resolve_palette()`’s `manual_colors`
argument, and `reset_group_colors()` puts the picker back to it on
Reset.

### Debouncing Free Text

`textInput()` and `textAreaInput()` report on **every keystroke**, so a
plot that reads one directly is rebuilt once per character - and for a
gene list or an expression, most of those characters are a state the
plot cannot use. Use `.sci_debounced_input(input, "key", params)`
(`R/input_helpers.R`), created **once** in the module server body;
inside another reactive it rebuilds the timer and does nothing. 700ms
matches VizModules. Select, numeric, checkbox and slider inputs report
discrete choices and need nothing.

### CSS Containment

Any stylesheet or inline `tags$style()` this package ships lands in the
host app’s document. There is no shadow DOM and no automatic scoping,
and every plot module pulls a colour picker in, so one bare selector
restyles an app that merely wanted one plot. VizModules was bitten by
this three times (#355).

Anchor every rule on a class this package invents - `.scivizmodules-` or
`.sci-`. **Judge by the leftmost class: if you did not invent it, the
rule is not scoped.** `.navbar`, `.well`, `.nav-tabs`, `.form-group`,
`.selectize-dropdown`, `.option`, `.btn` and friends are Bootstrap’s,
selectize’s or DT’s, not yours.

Layout belongs in a stylesheet, not an inline `style=` (which a host app
can only override with `!important`); per-instance values go through a
CSS custom property. Do not assume the parent’s padding - use `gap`, and
`min-width: 0` on flex children. A dropdown or popover parented to
`<body>` cannot be reached by a descendant selector, so give it a marker
class of its own.

This package currently ships no package-level CSS; the only stylesheet
is the module gallery’s
([`.sci_gallery_css()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_gallery_css.md)
in `R/moduleGallery_app.R`), every rule scoped to
`.scivizmodules-gallery` - `tests/testthat/test-module-gallery.R` checks
that. Keep it that way.

### Adding a Module: Gallery, App and Figure Builder

Every module is in the gallery. Its entry in
[`.sci_module_showcase()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_module_showcase.md)
(`R/module_showcase.R`) is part of the module, not an afterthought: one
entry gives it its gallery tab and Overview card, the example its
`*App()` opens on, and, for a data-frame module, its Figure Builder
entry. `tests/testthat/test-showcase.R` derives the package’s modules
from its exports (every `X` with `XInputsUI`, `XOutputUI`, `XServer` and
`XApp` exported) and fails, naming the module, when one has no entry. So
when you add a module:

1.  **Add its showcase entry** with
    [`.sci_showcase_entry()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_showcase_entry.md):
    the module’s base name, its label and shorter tab label, its `group`
    (one of `.sci_gallery_groups`, the gallery’s menus), a one-line
    `description`, its `dataset`, its `kind` (`"df"` for a data frame
    fed through the gallery’s filterable table, `"object"` for anything
    else, with a `preview` function returning a data frame of it), and
    any Suggests it needs in `needs`.
2.  **Give it showcase `defaults` that switch on its distinctive
    features** - highlighted genes or variants, statistics, annotation
    tracks, splits, trajectories, fit lines - not just column mappings.
    The defaults must name real columns and values and be accepted by
    the controls they seed; `test-showcase.R` checks both, so a key no
    control reads fails as well.
3.  **Add a catalogue loader** to
    [`.sci_example_catalogue()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_example_catalogue.md)
    if the module brings new example data (list the Suggests it is read
    from in `needs`, and use `app_datasets` for further datasets its
    `*App()` should offer).
4.  **Open its `*App()` on the showcase example**: give it
    `defaults = NULL, hide.inputs = NULL, hide.tabs = NULL`, and when
    its data argument is `NULL`, take
    `example <- .sci_module_example("<id>", defaults)` and use
    `example$data_list` and `example$defaults`. Pass `defaults`,
    `hide.inputs` and `hide.tabs` on to `createModuleApp()` or the
    internal app factory, which drop the `NULL` ones
    ([`.sci_server_args()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_server_args.md))
    so a server’s own `hide.tabs` default survives. Document them with
    `@inheritParams volcanoPlotApp`.
5.  **Set `figure_builder = TRUE`** if it takes a data frame and renders
    plotly.
6.  **Add it to `_pkgdown.yml`** and to the module list in this file.
7.  **Open its tab in
    [`sciModuleGalleryApp()`](https://j-andrews7.github.io/sciVizModules/reference/sciModuleGalleryApp.md)**
    and check that it renders as intended on its showcase settings.

### Module Structure Pattern

Each module has at least 3 files: `*_module_ui.R` (InputsUI/OutputUI
functions), `*_module_server.R` (Server function), `*_module_app.R`
(`*App()` example). A 4th file of module-specific helpers is allowed,
e.g. `goFanPlot_helpers.R`. Standalone plotting functions get their own
file, e.g. `goFanPlot.R`, `cnSegmentPlot.R`.

Keep the plotting function usable on its own, independent of Shiny. The
module server should be a thin layer that maps inputs onto that
function’s arguments and then applies the shared VizModules finalize
stack.

Where the UI and server both need the same defaults or input choices,
factor them into a shared internal helper rather than duplicating the
literal in both files — the two drift otherwise (see
[`.cn_seg_base_defaults()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_cn_seg_base_defaults.md)
and friends in `R/cnSegmentPlot.R`).

### Critical Namespace Pattern for Wrapper Modules

``` r
wrapperServer <- function(id, data_reactive) {
    # Process data INSIDE moduleServer to access namespaced inputs
    filtered_data <- moduleServer(id, function(input, output, session) {
        reactive({ /* use input$customField here */ })
    })
    # Call base module OUTSIDE to avoid double-namespacing (id-id-inputName)
    baseModuleServer(id, filtered_data)
}
```

In UI: Use `NS(id)` for wrapper’s inputs, pass bare `id` to base module
UI functions.

## Common Issues

| Issue | Solution |
|----|----|
| “object not exported by namespace” | Run `devtools::document()` to regenerate NAMESPACE |
| `document()` rewrites the whole NAMESPACE | DESCRIPTION records `Config/roxygen2/version`. A newer installed roxygen2 reformats every entry and bumps the stamp. Keep the diff scoped: revert the unrelated hunks, or agree to the reformat deliberately rather than as a side effect |
| Linting failures | Check .lintr: 120 char lines, 4-space indents |
| “Non-standard file/directory” in check | Add to .Rbuildignore with regex pattern |
| Module inputs not responding | Namespace issue - verify NS(id) pattern (see above) |
| Vignette build errors | Install: `install.packages(c("knitr", "rmarkdown"))` |
| `'scattergl' objects don't have these attributes: 'hoveron'` | Benign plotly warning from `toWebGL()` on line traces; noisy in test output, not a failure |
| Faceted figure loses its draggable axis titles | `axis_titles_as_annotations()` intentionally skips multi-panel figures; use `apply_axis_title_to_annotations()` instead |
| “object ‘example_sce’ not found” in package code | No `LazyData`, so bundled datasets are not promises in the namespace. Use `.sci_example_data("example_sce")`; in an `@examples` block or a test, call [`data()`](https://rdrr.io/r/utils/data.html) first |
| A plot renders two or three times for one change | See “Avoiding Double Renders” above - pick the right one of reactive `defaults`, `freezeReactiveValue()`, or a server-side store |
| [`shiny::testServer()`](https://rdrr.io/pkg/shiny/man/testServer.html) cannot drive a plotly output | Expected; assert on the server’s own reactives instead, or verify structurally with [`plotly::plotly_build()`](https://rdrr.io/pkg/plotly/man/plotly_build.html) |
| `test-showcase.R` fails with “No gallery showcase entry for: …” | A module was added without its gallery entry. Add one to [`.sci_module_showcase()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_module_showcase.md) and open its `*App()` on it (see “Adding a Module: Gallery, App and Figure Builder”) |
| A showcase default “does nothing” | `get_default()` drops a value its control rejects and ignores a key no control reads; `test-showcase.R` reports both. Check the key against the module’s `*InputsUI()` docs |

## Critical Rules

1.  **Build upon VizModules whenever possible** - start from an existing
    VizModules module or helper; add only the scientific specialization
    this package owns. Verify the installed API before calling it.
2.  **NEVER edit NAMESPACE manually** - always use
    `devtools::document()`
3.  **ALWAYS run `devtools::document()`** after changing roxygen2
    comments or signatures
4.  **Run `devtools::test()`** after changes to verify the testthat test
    suite passes; also test modules interactively via example apps
5.  **Follow namespace pattern strictly** for wrapper modules (see
    Coding Conventions)
6.  **Strongly prefer plotly** - the shared finishing helpers,
    manual-edit persistence, the Figure Builder and the source-data
    images all assume a plotly figure, so a module built from scratch
    should be plotly unless plotly has no reasonable equivalent. A
    non-plotly htmlwidget with Shiny bindings is acceptable in that case
    (e.g. a 3D molecular viewer via NGLVieweR or r3dmol; VizModules’ own
    `ComplexHeatmap_Heatmap` is another). Such a module must say so in
    its docs, and supply its own image export. To appear in the Figure
    Builder export and source archive it needs `vector_svg` /
    `raster_png` renderers (built with `draw_to_svg()` /
    `draw_to_png()`); without them it contributes no artwork there
7.  **Document missing features** - clearly note functionality
    unavailable in plotly
8.  **Use
    [`VizModules::organize_inputs()`](https://j-andrews7.github.io/VizModules/reference/organize_inputs.html)**
    helper for consistent UI layouts
9.  **Keep changes scoped** - do not let generated-file churn (NAMESPACE
    reformatting, roxygen version bumps) ride along with a behavioral
    change
10. **Every module select is a `viz_select_input()`** - never
    [`shiny::selectInput()`](https://rdrr.io/pkg/shiny/man/selectInput.html).
    A column of gene names is unusable otherwise, and two VizModules
    0.5.0 fixes land only on the virtual select.
    `tests/testthat/test-select-inputs.R` enforces this
11. **Scope every CSS selector** on a class this package invents (see
    “CSS Containment”)
12. **Load the matching VizModules skill before module work** - adding,
    wrapping or wiring a module starts from `vizmodules-custom-module`,
    `vizmodules-new-module` or `vizmodules-app` (see “Use the VizModules
    Skills for Module Work”)
13. **Every module is in the gallery** - a new module ships with its
    [`.sci_module_showcase()`](https://j-andrews7.github.io/sciVizModules/reference/INTERNAL_sci_module_showcase.md)
    entry, showcase defaults that switch on its distinctive features,
    and an `*App()` that opens on them (see “Adding a Module: Gallery,
    App and Figure Builder”). `tests/testthat/test-showcase.R` enforces
    this

## Best Practices

- Avoid `sapply` usage, it is unsafe in package code. Prefer `vapply`
  with an explicit `FUN.VALUE`.
- When changing a shared plotting function, keep existing single-input
  behavior byte-identical unless the change is the point; the existing
  tests are the regression guard and should stay green untouched.
- Prefer verifying plotly output structurally
  ([`plotly::plotly_build()`](https://rdrr.io/pkg/plotly/man/plotly_build.html),
  then inspect `x$data` / `x$layout`) over eyeballing; reserve
  interactive checks for layout and legibility questions that structure
  cannot answer.
