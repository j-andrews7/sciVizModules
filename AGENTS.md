# Agent Instructions for sciVizModules

## Repository Overview

**sciVizModules** extends VizModules with interactivity-first Shiny modules for scientific analyses and plots. Prefer composition and extension of VizModules over parallel reimplementations of general plotting-module behavior.

**Stack**: R (>= 4.6.0), Shiny, VizModules (>= 0.5.0), plotly, roxygen2 | **Version**: 0.99.0 | **License**: MIT + file LICENSE

The package targets Bioconductor (see `biocViews` in DESCRIPTION and `BIOCONDUCTOR_SUBMISSION_PLAN.md`), so keep R CMD check clean and follow Bioconductor packaging conventions.

## Repository Structure

- **R/** - source files: `*_module_ui.R` (UI), `*_module_server.R` (logic), `*_module_app.R` (examples), plus `*_helpers.R` and standalone plot functions
- **man/** - Auto-generated roxygen2 docs
- **data/** - example datasets used by tests, examples, and vignettes
- **data-raw/** - scripts that build the example datasets
- **vignettes/** - `quick-start.Rmd`
- **tests/testthat/** - testthat tests, plus `testthat.R` to run the suite
- **inst/apps/** - standalone demo apps (e.g. the module gallery)
- **.github/workflows/** - `R-CMD-check.yaml` and `pkgdown.yaml`
- **DESCRIPTION** - Package metadata and dependencies
- **NAMESPACE** - Generated by roxygen2 (NEVER EDIT MANUALLY)
- **.lintr** - Line length: 120 chars, indentation: 4 spaces
- **.Rbuildignore** - Files excluded from package build

## Coding Conventions

### VizModules Foundation

VizModules is a hard dependency (`Depends: VizModules (>= 0.5.0)`) and the primary foundation for generic interactive plotting, UI organization, downloads, annotations, and module infrastructure.

- Before building or changing a module, first check whether an existing VizModules module, helper, or wrapper pattern covers the general behavior. Extend it with science-specific defaults, controls, data preparation, annotations, or validation instead of recreating it.
- Every VizModules plot module follows the shared `*InputsUI(id, ...)`, `*OutputUI(id)`, and `*Server(id, data = reactive(...), ...)` contract. Preserve this contract when wrapping or composing a base module.
- Use `defaults` to set scientific defaults. Use `hide.inputs` and `hide.tabs` to enforce fixed values without exposing the corresponding generic controls.
- Prefer documented VizModules arguments and helpers over local replacements. Commonly useful ones: `organize_inputs()`, `module_tack_ui()`, `get_default()`, `hide_input()`, `viz_select_input()` / `update_viz_select()`, `setup_reactive_defaults()`, `setup_auto_update_logic()`, `apply_title_layout()`, `create_axis_styles()`, `apply_subplot_axis_styling()`, `axis_titles_as_annotations()`, `apply_axis_title_to_annotations()`, `add_reference_lines()`, `add_plot_config()`, `apply_render_margins()`, `empty_plot()`, `collect_source_data()`, `create_source_download_handler()`, and the reset helpers (`reset_axes_inputs()`, `reset_plotly_inputs()`, `reset_lines_inputs()`).
- For faceted / multi-panel figures, reuse the facet toolkit rather than hand-rolling layout maths: `resolve_facet_sharing()`, `resolve_facet_layout()`, `apply_facet_subplot_spacing()`, `build_facet_annotations()`, and `build_facet_panel_borders()`.
- For a new scientific module, create bespoke plotting or module code only when VizModules does not provide an appropriate base. Reuse its input organization, layout, download, and plotly conventions where applicable.
- All plots must remain plotly-based. Do not assume that every argument of an underlying `dittoViz`, `dittoSeq`, or `plotthis` function is exposed through a VizModules module; verify its documented signature first.

### VizModules Reference Sources

Use these sources before guessing at a VizModules API or adding a replacement helper:

1. Installed package help and vignettes: `help(package = "VizModules")`, `vignette("quick-start", package = "VizModules")`, `vignette("custom-modules", package = "VizModules")`, and `vignette("adding-a-new-module", package = "VizModules")`.
2. The source itself, which is often checked out alongside this repo at `../VizModules`. Reading `R/*.R` there is the fastest way to confirm exact helper behavior and argument semantics.
3. Package website and reference: https://j-andrews7.github.io/VizModules/ and https://j-andrews7.github.io/VizModules/reference/.
4. Repository: https://github.com/j-andrews7/VizModules.

Check the installed version with `packageVersion("VizModules")` before relying on a helper; this package tracks it closely and helpers are added often.

Base modules available in VizModules: `ComplexHeatmap_Heatmap`, `dittoViz_freqPlot`, `dittoViz_scatterPlot`, `dittoViz_yPlot`, `dumbbellPlot`, `linePlot`, `parallelCoordinatesPlot`, `piePlot`, `plotthis_AreaPlot`, `plotthis_BarPlot`, `plotthis_BoxPlot`, `plotthis_DensityPlot`, `plotthis_DotPlot`, `plotthis_Histogram`, `plotthis_SplitBarPlot`, `plotthis_ViolinPlot`, `radarPlot`. Run the matching `*App()` function to inspect a module interactively when useful.

### Module Structure Pattern

Each module has at least 3 files: `*_module_ui.R` (InputsUI/OutputUI functions), `*_module_server.R` (Server function), `*_module_app.R` (`*App()` example). A 4th file of module-specific helpers is allowed, e.g. `goFanPlot_helpers.R`. Standalone plotting functions get their own file, e.g. `goFanPlot.R`, `cnSegmentPlot.R`.

Keep the plotting function usable on its own, independent of Shiny. The module server should be a thin layer that maps inputs onto that function's arguments and then applies the shared VizModules finalize stack.

Where the UI and server both need the same defaults or input choices, factor them into a shared internal helper rather than duplicating the literal in both files — the two drift otherwise (see `.cn_seg_base_defaults()` and friends in `R/cnSegmentPlot.R`).

### Critical Namespace Pattern for Wrapper Modules

```r
wrapperServer <- function(id, data_reactive) {
    # Process data INSIDE moduleServer to access namespaced inputs
    filtered_data <- moduleServer(id, function(input, output, session) {
        reactive({ /* use input$customField here */ })
    })
    # Call base module OUTSIDE to avoid double-namespacing (id-id-inputName)
    baseModuleServer(id, filtered_data)
}
```

In UI: Use `NS(id)` for wrapper's inputs, pass bare `id` to base module UI functions.

## Common Issues

| Issue | Solution |
|-------|----------|
| "object not exported by namespace" | Run `devtools::document()` to regenerate NAMESPACE |
| `document()` rewrites the whole NAMESPACE | DESCRIPTION records `Config/roxygen2/version`. A newer installed roxygen2 reformats every entry and bumps the stamp. Keep the diff scoped: revert the unrelated hunks, or agree to the reformat deliberately rather than as a side effect |
| Linting failures | Check .lintr: 120 char lines, 4-space indents |
| "Non-standard file/directory" in check | Add to .Rbuildignore with regex pattern |
| Module inputs not responding | Namespace issue - verify NS(id) pattern (see above) |
| Vignette build errors | Install: `install.packages(c("knitr", "rmarkdown"))` |
| `'scattergl' objects don't have these attributes: 'hoveron'` | Benign plotly warning from `toWebGL()` on line traces; noisy in test output, not a failure |
| Faceted figure loses its draggable axis titles | `axis_titles_as_annotations()` intentionally skips multi-panel figures; use `apply_axis_title_to_annotations()` instead |

## Critical Rules

1. **Build upon VizModules whenever possible** - start from an existing VizModules module or helper; add only the scientific specialization this package owns. Verify the installed API before calling it.
2. **NEVER edit NAMESPACE manually** - always use `devtools::document()`
3. **ALWAYS run `devtools::document()`** after changing roxygen2 comments or signatures
4. **Run `devtools::test()`** after changes to verify the testthat test suite passes; also test modules interactively via example apps
5. **Follow namespace pattern strictly** for wrapper modules (see Coding Conventions)
6. **All plots must use plotly** - this is a plotly-based package
7. **Document missing features** - clearly note functionality unavailable in plotly
8. **Use `VizModules::organize_inputs()`** helper for consistent UI layouts
9. **Keep changes scoped** - do not let generated-file churn (NAMESPACE reformatting, roxygen version bumps) ride along with a behavioral change

## Best Practices

- Avoid `sapply` usage, it is unsafe in package code. Prefer `vapply` with an explicit `FUN.VALUE`.
- When changing a shared plotting function, keep existing single-input behavior byte-identical unless the change is the point; the existing tests are the regression guard and should stay green untouched.
- Prefer verifying plotly output structurally (`plotly::plotly_build()`, then inspect `x$data` / `x$layout`) over eyeballing; reserve interactive checks for layout and legibility questions that structure cannot answer.

Trust these instructions - only search for additional info if incomplete or incorrect.
